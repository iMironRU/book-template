# Runnable-листинги в книгах: концепция и бэклог `book-template`

> Свод архитектурных решений по интеграции книг серии «Школа 1С-инженеров» с песочницей BSLexicon, статическим анализатором bsl-language-server и сокращателем ссылок Ярлыкон.  
> Документ описывает изменения, которые ложатся в `book-template`. BSLexicon-овский бэклог оформляется отдельно.

---

## 1. Контекст и цель

Книги серии содержат большое количество примеров кода на BSL. У текущей раскладки три проблемы:

1. **Нет runnable-примеров.** PRIMM-методология (Predict → Run → Investigate → Modify → Make), на которой явно строится BSLexicon и неявно — обучающие книги, требует, чтобы код **запускался** прямо во время чтения. Без этого «Run» выпадает.
2. **Читатель не знает, куда вставить код.** Это типовая проблема начинающего: листинг есть, а ментальной модели «куда это идёт» нет. В голове опытного автора эта информация очевидна и поэтому часто опускается.
3. **Код в книге не валидируется автоматически.** Опечатки, устаревший синтаксис, переименованные функции — всё это всплывает только когда читатель отрывает голову об экран. Контур у книги должен быть таким же, как у нормального продукта: CI с фейлом при ошибках.

**Решение** — связка четырёх инфраструктурных элементов:

```
       книга (репозиторий)
              │
              │  fenced-блоки `bsl` с метаданными
              ▼
       book-template (pre-build pipeline)
              ├──▶ bsl-language-server   (валидация синтаксиса/диагностики)
              ├──▶ Ярлыкон               (короткие URL для печатной версии и QR)
              └──▶ BSLexicon             (целевой URL для runnable-листингов)
```

Все доработки этого документа касаются исключительно **книжного контура**. Это не часть edu-framework, не часть Univerkon, не общая платформа 1С. Скоуп узкий и осознанный.

## 2. Типология листингов

У каждого fenced-блока с BSL есть тип. Типов ровно три, четвёртого выдумывать нельзя:

| Тип | Что это | Открывается в песочнице | Валидируется bsl-language-server | Требует `@место` |
|---|---|---|---|---|
| `runnable` | Чистый язык. Не использует справочников, документов, форм, регистров. Самодостаточен. | да | да | нет |
| `contextual` | Требует платформенного приёмника (модуль формы, обработчик команды, регламентное задание и т.п.). | нет | да, в режиме «допускаем платформу» | да |
| `conceptual` | Демонстрирует идею, синтаксис или антипаттерн. Не предназначен для запуска. Может быть намеренно неполным или сломанным. | нет | нет | нет |

Тип — единственный обязательный атрибут листинга. Без него сборка не должна проходить.

## 3. Метаданные листинга

### 3.1. Принцип разделения

У листинга две разные группы метаданных, и они служат разным потребителям:

1. **Режим рендера** — нужен **сборщику книги** до того, как он смотрит внутрь кода. Решает: запускать ли в песочнице, гнать ли через bsl-language-server, рисовать ли кнопку «Открыть», рисовать ли плашку «Куда вставить».
2. **Контекст вставки** — нужен **человеку, который копирует код к себе в 1С**. В какой модуль, в какой обработчик, на клиент или сервер.

Граница между ними:

> **Что должно путешествовать с кодом — лежит в коде; что является инструкцией сборщику — лежит вне кода.**

Конкретно:

- **Режим рендера** живёт в info-string fenced-блока: ` ```bsl contextual `.
- **Контекст вставки** живёт в комментариях `//@` в самом начале листинга, до первой не-комментарной строки.

### 3.2. Пример

````markdown
```bsl contextual
//@место: модуль формы документа.ЗаказКлиента / обработчик команды
//@команда: Заполнить
//@директива: &НаКлиенте

&НаКлиенте
Процедура Заполнить(Команда)
    ОчиститьСообщения();
    ...
КонецПроцедуры
```
````

Здесь:

- `contextual` в info-string говорит сборщику: «не рисуй кнопку „Открыть в песочнице“, валидируй на наличие `@место`, прогони через bsl-language-server в режиме „допускаем платформенные обращения“».
- `//@место`, `//@команда`, `//@директива` — это инструкция читателю. Когда он скопирует листинг к себе и вставит в модуль, комментарии останутся рядом с кодом — память не подведёт. Сборщик использует их же, чтобы отрендерить плашку «Куда вставить» над листингом в книге.

### 3.3. Формат in-code метаданных

Строгий, машиночитаемый. Без излишеств:

```
//@<ключ>: <значение>
```

- Один ключ — одна строка.
- Все `//@…` строки должны идти подряд, в самом начале листинга, до первой строки кода или пустой строки.
- Ключи — латиница нижнего регистра (`место` → `mesto`? — нет, **ключи на русском**, потому что вся остальная нотация книги тоже на русском, не ломаем визуальную цельность).
- Значения — произвольный текст до конца строки.
- Регистр ключа значения не имеет (`//@МЕСТО:` ≡ `//@место:`), нормализуется при парсинге.

### 3.4. Ключи контекста (стартовый набор)

| Ключ | Назначение | Обязателен для |
|---|---|---|
| `@место` | Архитектурное место кода: общий модуль, модуль формы, обработчик команды и т.д. | `contextual` |
| `@команда` | Имя команды или обработчика, если применимо. | по необходимости |
| `@директива` | `&НаКлиенте`, `&НаСервере`, `&НаКлиентеНаСервереБезКонтекста` и т.п. | по необходимости |
| `@форма` | Имя формы или её путь, если код относится к конкретной форме. | по необходимости |
| `@подсистема` | Подсистема, в рамках которой работает код. | опционально |
| `@см` | Ссылка на смежный листинг или раздел книги. | опционально |

Список открытый. Новые ключи добавляются в словарь (см. §4) с явным описанием.

### 3.5. Правила согласованности (валидация при сборке)

CI book-template обязан проверять:

1. У каждого `bsl`-листинга есть тип в info-string (`runnable` | `contextual` | `conceptual`). Без типа — ошибка.
2. У `runnable`-листингов комментариев `//@место` быть не должно. Бессмысленно: чистый язык не привязан к платформе. Наличие — ошибка.
3. У `contextual`-листингов комментарий `//@место` обязателен. Отсутствие — ошибка.
4. У `conceptual`-листингов `//@место` опционален.
5. Значение `//@место` валидируется по словарю мест (§4). Неизвестное место — ошибка (или предупреждение на старте, ошибка после прогрева словаря).
6. Если info-string содержит неизвестный режим или лишние токены — ошибка.

## 4. Словарь «мест кода 1С»

Единый источник правды по архитектурным местам, в которые может попасть код.

### 4.1. Расположение

```
book-template/
  dictionaries/
    places.yaml          # словарь мест
    places.schema.json   # JSON-схема для валидации records
```

### 4.2. Структура записи

```yaml
- id: модуль-формы.обработчик-команды
  name: "Модуль формы / обработчик команды"
  description: >
    Процедура-обработчик команды формы. Выполняется на клиенте по умолчанию,
    может вызывать серверные методы через директивы.
  context:
    - модуль формы
  requires:
    - команда           # обязательно указать имя команды
  allows:
    - директива         # типично &НаКлиенте
    - форма
  example_directive: "&НаКлиенте"
  notes: >
    Если команда передаёт работу на сервер, оформляется парой клиент → сервер.
```

Поля:

- `id` — стабильный машинный идентификатор. Используется в значении `//@место:` (короткая форма) и в фильтрах.
- `name` — человекочитаемое имя для рендеринга в книге.
- `description` — короткое объяснение, что это за место.
- `context` — иерархия (общий модуль, модуль объекта, модуль формы и т.д.).
- `requires` — какие in-code ключи **обязаны** присутствовать (например, для обработчика команды обязателен `@команда`).
- `allows` — какие in-code ключи допустимы.
- `example_directive` — типичная директива компиляции.
- `notes` — методические уточнения.

### 4.3. Принципы наполнения

- Стартовый набор — самые частые места в типовом коде: общий модуль (клиентский / серверный / общего назначения), модуль формы, модуль объекта, обработчик команды, обработчик подписки на событие, регламентное задание, общий модуль внешнего соединения.
- Дополняется по мере появления новых листингов в книгах.
- Удаление записи — breaking change для всех книг. Только через явный rename + миграция.

## 5. Сборочный пайплайн

Pre-build хук, который вызывается до Pandoc/LaTeX-сборки книги.

### 5.1. Шаги

```
1. Сканирование .md-файлов книги
       │
       ▼
2. Извлечение fenced-блоков ```bsl ...```
       │
       ▼
3. Парсинг info-string → режим рендера
       │
       ▼
4. Парсинг in-code хедера //@... → контекст вставки
       │
       ▼
5. Валидация согласованности (§3.5)
       │
       ▼
6. Прогон тела листинга через bsl-language-server
       │  (с профилем book.bsl-language-server.json)
       │
       ▼
7. Для runnable:
       - формирование URL: <BSLEXICON_BASE>/?code=<base64(тело)>&source=<url-листинга>
       - укорочение через Ярлыкон API → короткий URL
       - генерация QR (для печатной версии)
       │
       ▼
8. Подготовка артефактов рендера:
       - плашка «Куда вставить» (для contextual)
       - кнопка/ссылка «Открыть в песочнице» (для runnable)
       - QR-код в подвале страницы (для печатной версии runnable)
       │
       ▼
9. Передача артефактов в Pandoc-фильтр / LaTeX-пайплайн
```

### 5.2. Поведение при ошибках

- **Ошибка валидации согласованности** (§3.5) — сборка падает с указанием файла, строки и причины.
- **Ошибка bsl-language-server уровня ERROR** — сборка падает.
- **Предупреждение bsl-language-server уровня WARNING** — выводится в лог, сборка проходит. Накопление >N предупреждений (порог настраивается) — сборка падает.
- **Недоступен Ярлыкон** — fallback на длинный URL. Сборка проходит с предупреждением.

### 5.3. Когда запускать

- Полный пайплайн — pre-release и nightly.
- На каждом push — только §1–§5 (синтаксическая валидация без обращения к внешним сервисам). Это быстро и не зависит от сети.

## 6. Профиль bsl-language-server для учебного кода

Учебный код намеренно простой, явный и многословный — он демонстрирует одну идею за раз. Часть штатных диагностик bsl-language-server для такого кода — шум.

### 6.1. Расположение

```
book-template/
  configs/
    book.bsl-language-server.json
```

### 6.2. Приглушаемые правила (стартовый набор)

- `cognitive-complexity` — учебные примеры могут быть «слишком простыми» по метрикам сложности, это норма.
- `magic-number` — в листингах магические числа допустимы как часть упрощения.
- `function-name-length` / `procedure-name-length` — учебные имена могут быть короткими (`Тест1`, `Пример`).
- `commented-code` — комментарии `//@` могут быть приняты за закомментированный код; настроить исключение по префиксу или приглушить правило.
- `using-modality` — учебные примеры часто используют `Сообщить()`, что для production-кода считается модальностью.
- `unused-parameters` — в обработчиках команды параметр `Команда` часто не используется.

### 6.3. Допущение платформенных обращений для contextual

bsl-language-server изначально допускает их. Это поведение нужно сохранить — выключать «strict mode» для проверки чистого языка не требуется, потому что `runnable` блоки и так чистый язык, а у `contextual` блоков валидация в основном синтаксическая.

### 6.4. Эволюция конфига

- Каждое новое правило, которое попадает под «шум для учебного кода», документируется в комментарии прямо в JSON.
- Любое приглушённое правило — это **педагогический компромисс**, который должен быть осознанным. Не «убрали, чтобы не мешало», а «убрали, потому что для учебных целей метрика неприменима».

## 7. Связь с BSLexicon

book-template **потребляет** публичный URL-контракт BSLexicon. Сам контракт документирован на стороне BSLexicon (`docs/book-integration.md`), не дублируется здесь.

book-template ожидает:

- Параметр `?code=<base64>` — преднаполнение редактора.
- Параметр `?source=<url>` — отрисовка provenance-баннера.
- Параметр `?embed=1` — встроенный режим без шапки/футера (для web-версии книги, inline iframe).

book-template **формирует** URL и **не делает ничего сверх этого**. Если BSLexicon меняет контракт — book-template обновляет генератор; это контролируемая поверхность.

## 8. Связка с Ярлыконом

### 8.1. Зачем

- Печатная версия книги: длинный URL c base64-кодом не помещается ни на страницу, ни в QR-код приемлемой плотности. Короткая ссылка решает обе задачи.
- Метрики: какие листинги читатели реально открывают. Полезно для второго издания.
- Стабильность ссылок: если параметризация URL BSLexicon изменится, короткая ссылка остаётся той же, а целевой URL подменяется на стороне Ярлыкона.

### 8.2. Namespace

Книжные ссылки идут под отдельным префиксом, например `https://ya.imiron.ru/b/<id>`. Это даёт:

- визуальное отличие книжных ссылок от прочих;
- возможность фильтровать аналитику по book-домену;
- возможность ввести специфичные для книг правила (срок жизни, политика 404, и т.д.).

### 8.3. Контракт API

book-template вызывает Ярлыкон через HTTP API. Если API недоступен — fallback на длинный URL (см. §5.2).

Точный контракт API — на стороне Ярлыкона; здесь только то, что book-template ожидает: «дай короткий URL по длинному, опционально с book-namespace и метаданными (id книги, id листинга)».

## 9. Стандарт типографики

Параллельная задача, формально не связанная с runnable-листингами, но раскатка её **должна** идти одной волной с этим документом, потому что:

- Plашки «Куда вставить» и кнопки/QR «Открыть в песочнице» — это типографские объекты, у которых должен быть единый стиль на всю серию.
- При sweep-проходе по репозиториям книг (см. §11) логично заодно подтянуть оформление.

Подробности — отдельный документ `typography.md` в `book-template`. Здесь только обозначается связь.

## 10. Бэклог `book-template`

Что добавляется в репозиторий. Порядок — примерный приоритет.

- [ ] **Этот документ** (`docs/runnable-listings.md`) — первый артефакт, фиксирует решения.
- [ ] `dictionaries/places.yaml` — словарь мест кода (стартовый набор: 10–15 самых частых записей).
- [ ] `dictionaries/places.schema.json` — JSON-схема для словаря, для валидации в CI.
- [ ] `docs/listing-metadata.md` — отдельная памятка для авторов: как размечать листинги, какие есть ключи, примеры.
- [ ] `configs/book.bsl-language-server.json` — книжный профиль диагностик.
- [ ] `tools/extract-listings.{ts|py|js}` — извлечение fenced-блоков из .md.
- [ ] `tools/validate-listings.{ts|py|js}` — валидация согласованности (§3.5) и соответствия словарю.
- [ ] `tools/lint-listings.{ts|py|js}` — обёртка над bsl-language-server CLI: вход — список листингов, выход — JSON-репорт с привязкой к (файл, строка) книги.
- [ ] `tools/generate-sandbox-links.{ts|py|js}` — формирование URL BSLexicon, обращение к API Ярлыкона, генерация QR.
- [ ] `filters/insertion-place.lua` (или эквивалент для выбранного рендерера) — Pandoc-фильтр для плашки «Куда вставить».
- [ ] `filters/sandbox-button.lua` — фильтр для кнопки «Открыть в песочнице» (web) и QR-кода (print).
- [ ] `.github/workflows/listings.yml` — CI: парсинг + валидация + lint на каждом push; полный пайплайн nightly.
- [ ] `docs/typography.md` — стандарт типографики (выносится отдельной задачей, упоминается тут как зависимость).

## 11. План раскатки

1. **Концепт → book-template.** Этот документ кладётся в `book-template/docs/runnable-listings.md`. Все нижеследующие артефакты живут в этом же репозитории.
2. **Реализация артефактов** по бэклогу §10. Не обязательно строго по порядку, но словарь мест и валидатор согласованности — фундамент, без них остальное не имеет смысла.
3. **Sweep по репозиториям книг.** По одной книге:
   - инвентаризация существующих листингов;
   - разметка типа (`runnable` / `contextual` / `conceptual`);
   - добавление `//@место` для `contextual`;
   - прогон через CI book-template;
   - правка типографики под новый стандарт.
4. **Обратный поток в book-template.** На каждой книге обнаружатся места, которых нет в словаре или не покрыты валидатором. Эти доработки возвращаются в book-template — так словарь и инструменты дозревают.
5. **Релиз серии.** Когда все книги приведены к единому стандарту — фиксируется минорная версия book-template и метка совместимости в каждой книге.

Чтобы не размывать фокус, явно отделяется:

- **BSLexicon-овский бэклог** — URL-контракт (`?code`, `?source`, `?embed`), provenance-баннер, embed-режим, документ `docs/book-integration.md` в самой BSLexicon. Оформляется отдельным файлом.
- **Ярлыкон-овский бэклог** — book-namespace, метрики, политика жизненного цикла ссылок. Оформляется отдельным файлом (если потребуется).
- **edu-framework.** Словарь мест кода — это книжный артефакт, не нормативный. В edu-framework не уезжает.
- **Прочие тренажёры / Дидатикон / Кабиторий.** Если им когда-то потребуется похожая разметка — будут смотреть на book-template как на референс, но книжная инфраструктура не претендует быть общей.
